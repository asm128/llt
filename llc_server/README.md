# LLC Server

Copied from llc_samples/llc_blitter_search as a starting project. Build llc_server.vcxproj through llt.slnx in Release/x64; the executable is llb/x64.Release/llc_server.exe. The current UI and functions are the Blitter Search implementation.

- Click **D: DRIVE** or browse folders in the left list. `cd PATH` in the console selects a folder directly.
- Click **INDEX DIRECTORY** to scan files beneath the selected folder. Progress shows files found and read; **CANCEL INDEX** stops the scan and keeps the previous searchable results. Click **INDEX DIRECTORY** again on the same folder to resume from the last completed shard.
- Type in the centered search field, including a single letter such as `A`. Matching files include content and relative path terms. Process and Windows service names are filtered from live snapshots. Multiple terms narrow file results.
- Click a file or result to select and preview it. Click **O** in the directory viewport to open the selected file in the file pane.
- Scroll or press PageUp/PageDown in the file pane to read through large files in 1 MiB windows. The file pane title shows the current byte offset and total length.
- Enter a command in the console to run it through LLC's process broker. `pwd`, `cd PATH`, `help`, and `clear` are handled by the app. On Windows, external commands start in the selected folder. One external command runs at a time; output is shown when it completes. The broker closes the child stdin after each command, so this is not a persistent shell session.

The on-disk index defaults to `llc_server.index` beside the executable. Pass `--index=ABSOLUTE_PATH` to use another index base path; omit the `.partial` suffix. At startup the app loads a completed index if present, otherwise its saved `.partial` checkpoint. The console identifies a partial index and its completed file count; search results from it cover only completed shards. Larger directories use the base file as a manifest for numbered word-index shards. New word shards use LLC deflate when it makes them smaller; existing uncompressed shards still load. A companion `.chars.GENERATION` file routes single-character searches directly to matching files. Per-shard `.gram.GENERATION.SHARD` files route exact two-, three-, and four-character searches. A small bucket directory lets a query read only its relevant range and postings. Sidecars are saved with new shards or rebuilt on demand from legacy shards; the first query that rebuilds them can take much longer. A longer single ASCII word first checks its initial and final four-character routes to skip impossible shards, then reads LLC's serialized word views in remaining shards for exact results without constructing owned word objects. Other queries use LLC's word resolver. Broad longer words and multi-term searches can still take substantially longer. A canceled scan keeps completed checkpoints and the previous searchable index. Resuming uses the original file list, so restart the index after files change. Choosing a different folder discards the prior partial scan. The app publishes a new manifest after all shards are saved and removes the previous generation after any active search finishes. Search runs in the background and adds results as each shard finishes; the status shows elapsed time and shard progress. A large file may span shards; search combines terms and deduplicates the file across them. Indexing reads text files in 1 MiB chunks, including content beyond 100 MiB. Paths remain searchable for files that cannot be read or contain NUL bytes. A saved D: snapshot of 563,148 discovered paths was indexed and searched in the rendered Windows GUI. The `jsonreader` query returned 5,118 matches after 591 shards in 25.6 seconds; results appeared progressively before completion. Folder navigation, file preview, result selection, and an inaccessible-folder error were also exercised in an isolated desktop. This does not establish that the current D: contents still match the saved snapshot. Linux `/proc` process enumeration and systemd service listing compile, but have not been verified in a running Linux GUI.
